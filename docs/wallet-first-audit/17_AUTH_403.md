# 17 — Auth 403s: the three layers that can refuse, and how to tell them apart

One document for a single thread of work: `/api/auth/challenge` returning 403.
It was written three times in three turns as each layer turned out to be mine. This
is the merged account.

## 1. Three layers can refuse, and they need opposite responses

A 403 on that path is the answer to "who refused", and the body — not the status
— identifies the answer.

| Body | Layer | Meaning | Fix |
| --- | --- | --- | --- |
| `{"error":"origin_not_allowed"}` | **our proxy** | the caller is cross-origin and not on the allowlist | set `POLYTOOLS_APP_ORIGINS` |
| `{"error":"upstream_403","detail":"…cf-ray=…"}` | **the edge in front of Polyester** | bot management refused a server-to-server call | Polyester allowlists our egress |
| `{"error":"permission_denied","detail":"uri is not permitted"}` | **Polyester's API** | the exchange refused the `uri` (C-1) | Polyester recognises our origin |
| HTML or empty body | **the host or a WAF** | the request never reached the app | resolve before debugging the app |

Polyester's API speaks Connect, so its own refusal is JSON `{code, message}`.
Anything else did not come from the API layer — that single fact is what makes
the table possible.

For a long time every one of these arrived at the UI as *"Polyester refused this
site's origin"*. That is why this took three rounds instead of one: the error
message pointed at the exchange when the defect was here.

## 2. Defects found and fixed

**B-1 · The client ignored `API_BASE`.** Every other module resolves its backend
through it; the auth client used a bare relative path. On the documented
static-plus-worker deployment that hits the static host, which has no backend.

**B-2 · The origin guard rejected the intended architecture.** The guard blocked
`Sec-Fetch-Site: cross-site`, but in that deployment the app *is* cross-origin to
the worker, so the header was present on every legitimate call. It assumed a
same-origin deploy, which only holds for Cloudflare Pages Functions.

**B-3 · Cross-origin login needed a CORS grant, not just the absence of a block.**
A JSON POST preflights; with no `Access-Control-Allow-Origin` the browser blocks
it before the body is sent.

**Fix:** a pinned `POLYTOOLS_APP_ORIGINS` — comma-separated exact origins, empty
by default (same-origin only, so Pages behaviour is unchanged). When set, the
matching origin is echoed **exactly, never `*`**, so only a named site can read a
challenge or a token; `Vary: Origin`; preflight answered only for allowed
origins. Malformed entries are ignored rather than widening the list.

**B-4 · Same-origin detection trusted a reconstructed URL.** The Vite dev
middleware rebuilt the request as `http://localhost${path}`, disagreeing with the
browser's `Origin` (`http://127.0.0.1:5204`), so an ordinary same-origin call was
classified cross-origin and 403ed. Typecheck was clean and all unit tests passed;
only a browser run caught it. Fixed in both places — the middleware now forwards
the real `Host`, and the check prefers the browser's own `Sec-Fetch-Site` verdict
over a derived URL. Side benefit: dev challenges now bind the correct `uri`.

## 3. The deployment that predates the code

Measured against the live site, before any of the above was believed:

| Request | Response | Reading |
| --- | --- | --- |
| `GET /api/health` | `200 {"ok":true,…}` | Functions are deployed on that origin |
| `GET /api/auth/challenge` | `404 {"error":"Unknown route: …"}` | this build has no auth routes |

That `Unknown route` string is `handler.ts` on `main`. On the branch the same GET
returns `405 {"error":"method_not_allowed"}`, because the route exists and rejects
non-POSTs. The branch carried twelve commits that were never merged, so a preview
built from `main` cannot answer the request. Worth stating plainly because it is
the one failure no client change can fix.

## 4. `upstream_403`: the edge, not the API

On the branch preview, the challenge call returned `{"error":"upstream_403"}` —
our fallback for an error with **no Connect body**. That proved the route was
deployed, the POST body survived the adapter, and the server reached Polyester.
It also proved the answer did not come from the API layer.

**Confirmed on the deployed preview** (`cf-ray=a514e09d6d7fa7e5-DEL`):

```
{"error":"upstream_403","detail":"refused by a firewall in front of the API
 (HTML, no Connect body) · title=\"Access denied…\" · cf-error=1020 · cf-ray=…"}
```

Three things follow from the headers rather than from guesswork. The body was
HTML, so it did not come from Polyester's API, which speaks Connect JSON. There
was **no `cf-mitigated` header**, which Cloudflare sets on challenges — so this was
not a browser challenge. Cloudflare's `1020` is "access denied by a firewall rule".

That is a firewall refusing a datacenter-to-origin request, which is
indistinguishable from bot management at this level. This repo contains
corroboration: the third-party scripts examined earlier drive the same API through
`curl_cffi` with a **Chrome TLS fingerprint** specifically to pass Cloudflare. A
Worker cannot present a browser fingerprint.

The browser cannot substitute either — the exchange sends no
`Access-Control-Allow-Origin` to our origin, so the direct POST never leaves the
page. If both hold, no transport on our side fixes it, and the answer becomes a
Polyester conversation rather than a code change.

Refusals are now attributable: `describeUpstreamFailure()` reports the upstream
status, whether the body was HTML, whether it was a browser challenge, and the
`cf-ray` / `cf-mitigated` headers — the identifiers support needs to trace a
request. Markup is never echoed. The upstream call also sends `User-Agent` and
`Accept`, a common bot-management trigger; if the runtime rejects the header the
request is retried without it rather than failing.

## 5. Why the browser calls anything at all

Both calls go to our own backend on our own origin; Polyester is contacted by the
Worker, never by the page. On Pages Functions the origin is the same, so no CORS,
no preflight and no allowlist are involved.

The browser's only unavoidable step is the signature, because the wallet lives in
the browser and the server must never hold a key:

| Step | Where | Why |
| --- | --- | --- |
| challenge | server | the exchange must be called server-side |
| signature | **browser** | only the wallet can sign |
| token exchange | server | keeps the credential exchange off the client |
| token | memory only | discarded on reload |

## 6. Verifying a deployment in one command

```bash
node tools/check-deployment.mjs https://your-site.pages.dev 0xYourWalletAddress
```

Two read-only GETs plus one real challenge; no credentials, no wallet connection,
no signature. It prints a verdict for each row of the table in §1 and the next
action. Verified against four simulated deployments: an HTML 403 from an edge, an
HTML 403 with no `cf-` headers, a success, and a build predating the routes.

For the direct question — does the exchange accept our origin at all, independent
of the app — use `node tools/auth-gate-probe.mjs`, which asks the API itself from
a terminal.

## 8. One request that splits the remaining hypothesis

If the same call from an ordinary machine returns JSON, the block is specific to
our Worker's egress and Polyester can allowlist it. If it also returns an HTML
1020, the API refuses every non-browser client and the server-side design cannot
work as built.

```powershell
try { Invoke-RestMethod -Uri 'https://api.testnet.polyester.com/auth.v1.AuthService/CreateWalletChallenge' -Method Post -ContentType 'application/json' -Body '{}' }
catch { "STATUS: " + [int]$_.Exception.Response.StatusCode; $_.ErrorDetails.Message }
```

`{}` is deliberate: a reachable API answers with a Connect `invalid_argument`, and
an unreachable one answers with HTML. No wallet, no address, no signature.

## 9. What the developer docs offer, and why none of it bypasses the block

Read from the public docs at `testnet.polyester.com/docs/developer-docs`, rather
than inferred.

**Seven interfaces exist**: REST, WebSocket JSON, ConnectRPC, WebSocket Protobuf,
SBE WebSocket, FIX Classic and FIX-SBE. Only REST and ConnectRPC carry
request–response auth; the rest are market-data or institutional trading
transports.

**REST is a different representation on the same host.** The published reference
for the login call is:

```
POST https://api.testnet.polyester.com/v1/auth/wallet-challenge
```

Same origin, same edge. REST and ConnectRPC differ in encoding and path, not in
where the request lands — so switching transport cannot get around a firewall rule
keyed on IP or TLS fingerprint. It could only help if the rule were keyed on the
ConnectRPC path, which is untested and is settled faster by the control probe in
§8: if an ordinary machine gets a Connect response, the block is about the caller,
not the path.

**Ed25519 API keys do not remove the need to log in.** They are the server-side
credential for private requests, and the docs are explicit that creating one
requires *"an interactive JWT session"* — which requires wallet login. There is no
bootstrap path that skips it. Two details are still useful:

- keys support an `ipWhitelist` of up to 32 CIDRs, resolved from the network
  connection rather than client headers — so pinning a caller by IP is a thing
  this platform already does, which makes the ask in §8 ordinary rather than novel;
- API keys and interactive sessions are distinct session types, and an API key
  cannot satisfy an interactive MFA requirement.

**MFA is not in our path.** It gates API keys, withdrawals, policies, address-book
mutations and membership changes. Wallet login is a primary session and needs no
factor, so nothing here is blocked on MFA enrolment.

The `x-polyester-mock` header on the API playground returns canned responses. It is
a documentation feature and not something to build against.

### What the docs corrected in our code

The published challenge message ends with:

```
Resources:
- urn:polyester:wallet-challenge:login:eip155:888168:0x2222…
```

The account is the **last** colon-separated segment, after the `eip155:` namespace
and the chain id. Our URN parser read everything after `login:` as the address, so
it never matched the documented shape and fell back silently — the account-adoption
fix from the previous commit was inert. Corrected, and pinned by a test built from
the documented message verbatim.

The same reference confirms two things we had already changed: `purpose` must be
`LOGIN`, and `expiresAt` is an RFC 3339 string (`"2026-01-01T00:05:00Z"`).
